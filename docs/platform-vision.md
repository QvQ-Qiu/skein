# 前厅与后厂：小秋 × 雁阵的闭环愿景

> 2026-11-21 · 小秋是前厅，Skein 是后厂；用户只看见小秋，管理员看见控制台。

## 0. 一句话

**小秋负责“听见、回话、报进度”；Skein 负责“建单、派工、验收、自愈”。**
小秋不是第二个大脑，是雁阵伸进主站的手和嘴。

## 1. 现在走到哪

截至 2026-11-21，论坛前厅闭环已经跑通：

- 小秋 chat 里的 monitor 轮询帖子/评论，**所有吐槽都回**，bug/需求自动 intake 建单；
- Skein 派工/验收后按公开状态回写原帖，失败只记日志；
- chat 任务仍只记事件，不自动建单；显式转工单按钮的后端已就绪。

还缺的是“一条 thread 持续跟着一张单”：后续评论目前仍按新条目处理，没有订阅直通；用户也没有独立的进度页。
接口细节与已验证记录见 [`chat-events.md`](chat-events.md)。

## 2. 愿景：一个闭环，两个工作面

```text
用户 / 帖子 / 评论 / 聊天
        │
        ▼
小秋（前厅）── 识别、回执、追问、报进度
        │  intake（建单）
        ▼
Skein（后厂）── 工单、Router、工雁、验收、Watchdog
        │  outbound（状态）
        ▼
小秋（前厅）── 在原帖/原会话回写
        │
        ▼
用户（继续对话 / 确认 / 补充）

管理员 ── 控制台（验收/派工/配置）
       └─ 小秋 ops（自然语言操控，独立面）
```

**用户面对的始终是小秋；管理员面对的是控制台 + 小秋 ops。**
工单是两边共享的唯一“事”，thread_id 是这条事的上下文。

## 3. 权责划分

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| 集市用户 | 在帖子/评论/聊天里报障、提需求、追问、确认 | 看内部工单/transcript/diff；验收；派工；操作节点 |
| 小秋（公开面） | 识别意图；回执；追问复现信息；代用户建单；在原帖报公开进度 | 审批；合入；派工决策；看密钥/内部 diff；给用户发私信 |
| 小秋（ops 面） | 管理员专用：查单、派工、催办、暂停自动建单；后续只读转可写 | 绕过权限；自动合入；删除 pod；把内部信息发到公开面 |
| 管理员 | 验收/驳回；派工/取消；改准入/提示词；用 ops 对话操控 | 自动合入（硬闸）；把市场用户私有对话公开 |
| 工雁（worker） | 在节点 worktree 里改代码；回报分支/提交/diffstat/自测 | 合入；对外发言；读生产密钥；决定工单优先级 |
| Watchdog | 采集信号、自动建单、每日巡检、催办 | 对外发言；自动验收；改代码 |

## 4. 一条反馈的完整生命周期

1. **发现**：用户在帖子/评论/聊天里说“登录坏了”，可以 @ 小秋，也可以不 @。
2. **快筛**：小秋先用规则（@、报障词、管理员命令）过滤；拿不准再走 LLM 慢判。
   **所有吐槽都回**，但只有可执行的 bug/需求才建单；纯情绪吐槽只回执/记录。
3. **回执**：小秋在原帖回一句“收到，已登记 SK-XXXX，我先复现一下”，不承诺时间。
4. **建单**：小秋调 Skein `intake`，带上来源、thread_id、message_id、用户 sub、标题/摘要、分类/严重度、可见性。
5. **路由**：Skein 的准入/Router 决定受理、驳回或要补充；受理后派给节点上的工雁。
6. **执行**：工雁在 worktree 里修，产出分支/提交/diffstat/自测总结；不推送主分支。
7. **人审**：管理员在控制台验收；通过才合入/部署；驳回则回到工单。
8. **公开回写**：Skein 状态变化触发 outbound；小秋在原帖回“已定位/修复中/已修复”，只写公开摘要，不写内部细节。
9. **跟进（直通未做）**：用户在同一 thread 继续回复；现在按新评论再过一遍 monitor，
   后续改成 Thread 订阅直通，追加到原工单而不是重复建单。
10. **关闭/重开**：修复上线后小秋请用户确认；用户说没修好就重开；工单闭环。

## 5. 公开状态 vs 内部状态

内部（Skein 控制台）：

```text
staged → assigned → running → review → done / rejected
                 ↘ stalled（Watchdog 信号）
```

公开（小秋回帖）：

| 内部 | 公开 | 小秋话术 |
| --- | --- | --- |
| staged/assigned | 已收到 | “收到，已登记 SK-XXXX，我先复现一下。” |
| running | 处理中 | “已复现，正在修；有结论我在这条下面更新。” |
| review | 待确认 | “修好了，等维护者验收；通过后我回来说。” |
| done | 已修复 | “已修复并上线；你试一下，没好的话直接回我。” |
| rejected | 需补充 | “这条暂时没复现/不属于缺陷；能补充一下复现步骤吗？” |

公开面永远不出现：worker 日志、diff、内部评论、token、节点名、密钥。

### 语气

- **回执/进度/验收**：专业、短、只讲事实；不承诺时间，不夸大。
- **吐槽/情绪**：可以打趣、共情、像同事一样接话；但不嘲讽、不站队、不泄露内部。
- **所有吐槽都回**；纯情绪先接住，记录后判断要不要建单；有可执行的 bug/需求才建单。
- 不重复回执；同一 thread 只在关键状态变化时更新。

## 6. 接口契约（第一版）

### 6.1 小秋 → Skein：建单（已上线）

`POST /internal/intake`（`X-Skein-Token`）：

```json
{
  "source": "forum_post | forum_comment | chat",
  "thread_id": "帖子 ID（评论也填所属帖子 ID）",
  "message_id": "帖子或评论 ID",
  "requester": "forum:<userID>",
  "title": "登录坏了",
  "summary": "点登录按钮没反应，控制台 500",
  "category": "bug | request | venting",
  "severity": "low | normal | high",
  "visibility": "market",
  "dedup_key": ""
}
```

返回：`{ticket_id, code, status, public_status, created}`。Skein 负责去重、建 thread、
写 `origin/origin_id/requester/public_status` 与审计。

### 6.2 用户跟进：小秋 → Skein（未实现）

`POST /internal/tickets/{id}/followup`：带新消息文本、message_id、用户 sub。
Thread 已订阅时直通工单，不再走通用 Router。当前评论仍按新条目过 monitor。

### 6.3 Skein → 小秋：公开回写（已上线）

Skein 在派工/验收时直接调小秋
`POST {SKEIN_QA_CHAT_UPSTREAM}/internal/skein/notify`（`X-Skein-Token`），
带 `ticket_id/code/public_status/origin/origin_id`；小秋再调 Go 主站
`/internal/xiaoqiu/reply` 以机器人账号发到原帖。

- 同一张单、同一公开状态只发一次（按 `tickets.public_status` 去重）。
- 发送失败只记日志；尚未接入 outbox 重试。

### 6.4 管理员 ops 对话

小秋 ops 面（`/ops`）已有独立鉴权；给它一组**角色受限**的 Skein 工具：

- 只读：`list_tickets`、`ticket_detail`、`node_status`、`run_status`；
- 写：`dispatch`、`cancel`、`pause_auto_intake`、`run_job`（逐条加权限）；
- 验收：只做准备和摘要，真正“通过/驳回”仍是控制台按钮；或在对话里要求管理员二次确认 ticket code。
- 所有工具调用记审计：admin sub + 工具 + 参数 + 结果。

## 7. 自治分级

| 级别 | 小秋 | Skein | 人类 |
| --- | --- | --- | --- |
| L0 观察 | 只记录，不回 | 不建单 | 不介入 |
| L1 回执+建单 | 自动回执、建单 | 受理/派工 | 验收 |
| L2 分诊+追问 | 判分类/严重度、追问复现 | 自动派工 | 验收 |
| L3 主动修复 | 未被 @ 也发现高置信 bug；影子建单 | 后台修，修好才公开 | 验收 |
| L4 自动合入 | — | — | **永不做** |

- 公开面从 **L1** 开始；管理员/内部反馈可到 **L2**；L3 先只对内部、可开关。
- 自主性放在后厂：感知、路由、执行、自愈都可以自动；**验收权永远在人**。

## 8. 与原文档五模块的对应

| 原文档 | 我们现在的落点 | 小秋补什么 |
| --- | --- | --- |
| 双层架构 | Skein Router + 节点工雁 | 小秋是信道层/前厅，不是 Router |
| 事件驱动 | 论坛采集、chat 事件、Watchdog | 小秋做 Fast Path 识别 + 公开回执；Thread 订阅直通 |
| 面向人的交互 | 控制台四工作面 | 小秋是用户侧唯一入口；ops 是管理员侧对话入口 |
| 存算分离 | 控制面 A + 执行 pod | 小秋不存工单状态；只做无状态适配 |
| Watchdog | 信号、自动建单、每日巡检 | 小秋只负责把“需要人知道”的公开进度说出去 |

四个特征：

- **连续**：用户在主站/聊天/帖子里始终面对小秋；工单 thread 串起来。
- **高效**：小秋不阻塞，工雁并行；回执和修复解耦。
- **主动**：Watchdog + 小秋的公开面监测（L3）。
- **持久**：控制面 + 节点 + 小秋容器；任一前端挂了，工单还在。

## 9. 更好的办法（关键设计）

1. **小秋不是 Router，是 channel worker。** 它只有两个对外动作：`intake` 和
   `notify`；任务怎么拆、派给谁、什么时候停，全部由 Skein 决定。
2. **Thread 订阅直通（待做）。** 工单一开，原帖/原会话就是这条 Thread；后续评论直通工单，
   不再回到通用聊天，避免上下文丢失和重复建单。当前先按新条目再过 monitor。
3. **工单是唯一真相。** 小秋不维护“处理到哪了”的状态；状态只从 Skein 读，
   公开话术由模板生成。
4. **公开/内部两套状态机。** 公开只到“已收到/处理中/已修复/需补充”，
   内部才有 running/review/stalled。
5. **Outbox 幂等。** 每个公开状态只发一次；失败重试；同一 thread 不重复回执。
6. **投机执行只对内部/高置信。** 公开面先做 L1；L3 的影子修复只对管理员或
   高置信 bug 开启，避免对用户刷屏。
7. **管理员 ops 对话单独一面。** 公开 chat 永远拿不到 ops 工具；ops 只放管理员，
   写操作逐条授权 + 二次确认 + 审计。
8. **不自动合入。** 小秋可以回“已修复”，但“已修复”的前提是人已经验收/合入。

## 11. 护栏与失败模式

- **刷屏**：只对明确报障/需求回执；同一 thread 只回一次；限频；管理员可静音。
- **误判**：回执安全，建单可被管理员驳回；小秋不承诺时间；驳回话术不指责用户。
- **隐私**：公开只写模板化摘要；不引用聊天原文以外的内容；不暴露内部对象。
- **小秋挂了**：主站照常；Skein 可直接采集论坛事件（可选）；回执延迟。
- **Skein 挂了**：小秋可继续聊，intake 入队重试；不丢消息。
- **工雁/节点挂了**：Watchdog 建单/催办；小秋不谎报“修复中”。
- **用户删帖/改口**：工单保留快照；不再往已删 thread 回写。
- **重复报障**：dedup key 合并到同一工单；小秋只回执一次。

## 12. 指标

- 每天需要人工介入的次数；
- 误建单率（管理员驳回/关闭的比例）。
