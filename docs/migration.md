# 迁移路线

> 从今天的雁阵 v0.4.0 迁到 `docs/architecture.md` 的目标架构
> 原则：每一步单独可回滚；生产服务在切换前不停

## 0. 现状与目标

| | 今天 | 目标 |
| --- | --- | --- |
| 控制面 | Node 单进程（`server/`），单条分类器 | Python Router 宿主，常驻会话 + 空工具直答 |
| 工单 | `server/db.js` 的 SQLite | 同一库扩展后的领域库 |
| 会话 | cc 的 `--resume` 绑在节点本地 | Session 权威库（索引 + 内容寻址文件） |
| 准入 | 短文本硬闸 | 确定性矩阵（来源 × 点名 × 名单） |
| 通道 | 各作业直接写主站 | Outbox 统一出口，按回执幂等 |
| Watchdog | 采样 + 邮件 | 独立进程，只改 Worker 执行提示词，金丝雀 + 冻结 |

## 1. 切分顺序

| 步 | 内容 | 验收 | 回滚 |
| --- | --- | --- | --- |
| S1 | 控制面骨架：领域库、准入、空工具直答（**已完成**，`2f5c43f`） | 25 个测试通过 | 无生产影响 |
| S2 | Router 宿主循环：事件入口 + 直答 + 分派，接假 LLM | 端到端用 FakeLLM 跑通「聊天直答 / 事件分派」两条路 | 无生产影响 |
| S3 | 接真实模型网关，只读旁路运行（不派单、不写论坛） | 生产事件影子运行 7 天，对比分类结果与人工判断 | 关掉旁路 |
| S4 | 准入矩阵接管论坛评论采集（先只记账） | 每条事件都有 verdict，无遗漏 | 切回旧分类器 |
| S5 | Session 库 + transcript 同步 | 换节点能 `--resume`；未同步的会话被钉住 | 停同步，回到钉住状态 |
| S6 | Worker 改造：小秋的图与工具按 purpose 切分 | 对话 Worker 不直接写论坛；结果回 Router | 旧 chat 面继续跑 |
| S7 | Outbox 接管发帖与加精 | 同一天两次进入只出一篇；回执可对账 | 指回 8080 直连 |
| S8 | Watchdog 上线（先只观察，不写提示词） | 信号与人工判断对齐；误报可接受 | 停进程 |
| S9 | 打开 Watchdog 的提示词写入（金丝雀） | 一次真实修订走完 propose → canary → 稳定 | 冻结并回退 |
| S10 | 面板切换：雁阵 web 为骨架，并入 ops 四页 | 工单、Worker、节点、事件、告警五页可用 | 回旧面板 |

## 2. 切换日

S4 之后新旧控制面并存一段时间：旧 Node 进程继续跑工单，新 Python 宿主只做旁路。真正切换在 S6 完成、且旁路结果连续一周一致之后。

切换当天：

1. 停旧 Node 控制面，记录最后一张工单的 id。
2. 新宿主读同一份领域库（先确认迁移脚本已跑）。
3. 指向面板；验证工单、Worker、事件三页。
4. 观察 30 分钟；异常则停新宿主、起旧进程。

## 3. 不做的事

- 不迁论坛 MySQL。
- 不把工单迁进 PG。
- 不在同一窗口改面板与调度。

## 4. 服务器工作树布局

`/root/yanzhen` 里跑着**重构前**的雁阵（systemd 指向 `server/index.js`），所以它刻意**不跟随 `main`**：

| 分支 | 指向 | 用途 |
| --- | --- | --- |
| `prod-legacy` | 初始提交 `9cb672a` | 当前运行布局，`server/` `web/` `worker/` 原样保留 |
| `main` | 跟随 `origin/main` | 开发主线，含新的 `services/` 结构 |

部署新版本时**不要在这个目录里 checkout**，否则 `server/` 会被移走、systemd 失效。正确做法是把 `main` checkout 到新目录（例如 `/root/skein`），改好 unit 的 `WorkingDirectory` 与 `ExecStart`，再重启服务。

推送：服务器用仓库级部署密钥（`/root/.ssh/skein_deploy`），已写入仓库的 `core.sshCommand`，`git push` 直接可用。
